## 1. 서비스 개요

> **"가이드와 여행자가 만나는 디지털 광장"**

**Trip Agora(트립 아고라)** 는 개인 가이드가 자신만의 여행 코스를 상품(템플릿)으로 설계해 날짜가 정해진 여행을 열고, 여행자가 취향 기반으로 탐색·참가한 뒤, **여행 중에는 실시간 채팅·위치 공유·SOS로 그룹을 관리**하는 가이드-여행자 매칭 플랫폼이다. 이름의 '아고라'는 고대 그리스의 광장 — 사람이 모여 교류하는 공간 — 에서 왔다.

모집(마켓플레이스)과 진행(그룹 여행 운영 도구)을 하나의 앱으로 묶은 것이 핵심이다. 여행의 전 과정(상품 설계 → 모집 → 진행 → 리뷰)이 단일 플랫폼 안에서 순환한다.

### 1.1 문제 정의 (Problem)

1. **소통의 단절** — 단체 여행에서 가이드와 여행자가 분리되면 다시 만나기 어렵고, 길을 잃거나 긴급 상황이 생겨도 체계적으로 연락할 수단이 없다. 카카오톡 단체방은 있지만 위치 확인·긴급 호출 같은 여행 특화 기능이 없다.
2. **비효율적인 일정 관리** — 종이 일정표나 메신저 공지에 의존해, 일정 변경이 모든 참가자에게 신속·정확하게 전달되지 않는다.
3. **맞춤형 가이드 매칭의 부재** — 가이드는 여행사나 SNS·커뮤니티로만 찾을 수 있어, 취향(음식·사진·역사 등)에 맞는 가이드를 찾는 비용이 크고 신뢰 장치도 없다.

### 1.2 솔루션 (Solution)

| 문제 | Trip Agora의 해법 |
| --- | --- |
| 소통 단절 | 여행별 전용 방(Room)에서 그룹 채팅 + 전원 실시간 위치 공유 + FCM 푸시 기반 SOS 긴급 호출 |
| 일정 관리 | 가이드가 Day·시각·좌표 단위로 일정을 등록하고, 여행 중에도 수정할 수 있다 — 참가자 전원이 같은 일정을 열람 |
| 매칭 부재 | 태그(취향)·지역·날짜·키워드 조합 검색 + 가이드 프로필·평점·리뷰 시스템으로 탐색 비용과 신뢰 문제를 함께 해소 |

### 1.3 역할 전환 — 하나의 계정, 두 개의 모드

별도의 가이드 앱을 두지 않는다. 누구나 여행자로 가입하고, 마이페이지에서 **가이드로 전환**하면 즉시 상품 설계·모집·운영 기능이 열린다. 전환할 때 JWT를 새 역할 클레임으로 재발급하므로 서버의 권한 체계(URL 역할 규칙)와 앱의 화면 분기(가이드/여행자 탭)가 토큰 하나로 일관되게 움직인다. 여행자로 돌아간 뒤에 남아 있는 예전 가이드 토큰은 서버가 현재 역할을 확인해 거부한다. C2C 플랫폼의 고질적 문제인 공급자(가이드) 풀 확보를, 수요자(여행자)가 곧 공급자가 될 수 있는 구조로 푼 것이다.

## 2. 사용자 여정 (User Journey)

```
[공통]   소셜 로그인(카카오/네이버) → 닉네임·프로필 → 관심사 태그 3개 이상 선택
   │
   ├── [가이드 모드]
   │      마이페이지에서 가이드 전환 (프로필 자동 생성 + 토큰 재발급)
   │      → 가이드 프로필 작성 (소개·대표 이미지·SNS 링크)
   │      → 템플릿 설계: 빈 초안 생성 → 제목·소개·이미지·태그·지역 → Day별 일정(장소·시각·좌표)
   │      → 여행 열기: 시작일 + 정원 입력 (종료일은 일정 길이로 자동 계산, 템플릿의 일정·상품 정보를 여행 사본으로 복사)
   │      → 모집 마감 (시작 전에 직접, 또는 시작일에 자동) → 방(Room) 개설
   │      → 여행 진행 (채팅·위치·공지·일정 변경·SOS 대응)
   │      → 여행 종료(자동) → 리뷰 수신 → 평점이 템플릿과 프로필에 반영
   │
   └── [여행자 모드]
          검색 (키워드·날짜·지역·태그) → 여행 상세 → 참가 신청 (시작 전날까지, 즉시 확정) 또는 위시리스트 저장
          → 모집 마감 후 방 입장 → 여행 진행 (채팅·위치 공유·공지 확인·SOS 호출)
          → 여행 종료(자동) → 리뷰 작성 (별점 + 후기) → 지난 여행은 내 목록에서 숨길 수 있음
```

여행의 시작·종료는 사용자 액션이 아니라 **날짜의 경과**이므로, 스케줄러가 매일 자정에 상태를 바꾼다(한국 시간 00:00 시작일이 된 모집 중 여행 자동 마감, 00:01 시작, 00:03 종료). 사용자가 해야 하는 일은 여행 자체에 집중되어 있다.

## 3. 핵심 정책

| 정책 | 값 | 기획 의도 |
| --- | --- | --- |
| 참가 방식 | **선착순 즉시 확정** (승인제 없음) | 소규모 취향 여행의 가벼운 참여 장벽 유지. 대신 서버가 모집 상태·본인 여행 여부·중복 참가·기간 겹침·정원을 확인한다 |
| 정원·중복 보장 | 신청은 신청자와 여행 행을 순서대로 잠근 뒤 확인하고, 참가·찜은 (사용자, 여행) unique | 동시에 신청이 몰려도 정원을 넘기거나 같은 사람이 두 번 참가하지 않는다 |
| 모집 기간 | **시작 전날까지**. 시작일이 되면 가이드가 마감하지 않았어도 자동으로 마감되고 진행 중이 된다 | 출발한 여행에 뒤늦게 들어오거나, 마감을 잊은 여행이 계속 모집 중으로 남지 않게 |
| 참가 기간 겹침 금지 | 내 완료되지 않은 여행과 날짜가 겹치면 참가 불가 | 몸은 하나 — 물리적으로 불가능한 이중 참가를 서버가 차단 |
| 가이드 일정 겹침 금지 | 같은 가이드의 모집·마감·진행 중 여행과 기간이 겹치게 열 수 없다 | 위와 같은 원칙의 공급자 버전 |
| 방(Room) 개설 시점 | 모집 마감 시 | 참가자가 확정된 뒤에만 소통 채널이 열린다 — 모집 중 이탈·유입에 따른 방 관리 문제 원천 제거 |
| 방 접근 | 그 여행의 참가자만 (가이드 포함). 공지 작성·수정·삭제는 가이드만 | 방 번호를 알아도 참가자가 아니면 채팅·위치·공지에 접근할 수 없다 |
| 템플릿 수정 제한 | 모집·마감·진행 중 여행이 있으면 수정 불가. 여행을 한 번이라도 연 템플릿은 삭제 불가 | 모집 중 여행이 보여 주는 상품 정보와 템플릿이 어긋나지 않게, 지난 여행의 이력(참가·리뷰·채팅)이 사라지지 않게 |
| 여행의 독립성 | 여행을 열 때 템플릿의 **일정과 상품 정보(제목·소개·사진·지역·태그)를 여행 사본**으로 복사. 가이드 정보(닉네임·사진·평점)는 최신을 보여 준다 | 진행 중 여행의 일정 변경이 상품 원형을 바꾸지 않고, 템플릿을 고쳐도 지난 여행은 참가자가 보고 신청한 그대로 남는다. 사람 정보는 최신이 맞다 |
| 참가 취소 | 모집 중에만. 가이드는 자기 여행의 참가를 취소할 수 없다. 완료된 여행은 취소 대신 내 목록에서 숨김(기록 유지) | 확정된 그룹이 흔들리지 않게, 다른 참가자가 보는 이력과 인원이 그대로이게 |
| 리뷰 자격 | 완료된 여행의 여행자 참가자, 여행당 1건 | 실제 참가 경험에 기반한 평판만 축적 (가이드 셀프 리뷰·중복 리뷰 차단) |
| SOS | 진행 중인 여행의 참가자만. STOMP가 아닌 FCM 푸시로 같은 여행의 다른 참가자에게 | 긴급 신호는 여행 중에, 앱을 보고 있지 않은 사람에게도 닿아야 함 |
| 관심사 태그 | 사용자 최소 3개 · 템플릿 최대 5개 | 매칭 정확도의 하한(사용자)과 태그 남발 방지(상품)의 상한 |
| 회원 탈퇴 | 모집·마감·진행 중 여행에 참가 중이면 불가. 탈퇴하면 계정을 지우지 않고 개인정보를 비운다(익명화) | 다른 사람의 참가·리뷰·채팅 이력이 함께 사라지지 않게 |

## 4. 시스템 아키텍처

### 4.1 기술 스택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 클라이언트 | React Native + Expo (팀원 2인 개발) | 단일 코드베이스로 Android/iOS. 지도는 Naver Map SDK |
| 백엔드 | Java 17 · Spring Boot 3.5 | 도메인별 패키지, Controller–Service–Repository 계층 |
| 데이터 | MySQL 8 · Spring Data JPA + QueryDSL 5 | 복합 조건 검색만 QueryDSL, 단순 조회는 파생 쿼리. 연관 데이터는 배치 로딩(IN 조건으로 묶어서) |
| 실시간 | Spring WebSocket + STOMP (SockJS 폴백) | 채팅·위치 공유. 내장 SimpleBroker (단일 서버), 하트비트로 끊긴 연결 감지 |
| 푸시 | Firebase Admin SDK (FCM) | SOS 긴급 호출 |
| 스토리지 | AWS S3 | 프로필·템플릿 이미지 (UUID 키). 지우는 것은 DB 커밋 뒤 |
| 인증 | 소셜 로그인(카카오·네이버) + JWT (jjwt) | 자체 비밀번호 미보유. Access/Refresh, Refresh는 DB에 두고 재발급마다 교체 |
| 테스트 | JUnit 5 · Testcontainers(MySQL 8) · MockMvc | 실제 MySQL 위에서 API·동시성·쿼리 수를 검증 |
| 인프라 | AWS EC2 단일 인스턴스 · GitHub Actions | PR마다 테스트, main 반영 시 배포. `api.trip-agora.com` 도메인 운영 (현재는 종료) |

### 4.2 설계 의도

- **템플릿(원형)과 여행(인스턴스)의 분리** — 상품 재사용성과 진행 중 여행의 독립성을 함께 확보하는 구조의 축. 여행은 열릴 때 일정과 상품 정보를 사본으로 갖는다. 기준은 "그 시점의 기록인가, 최신 정보인가"다: 참가자가 보고 신청한 상품 정보는 기록(사본), 가이드 같은 사람 정보는 최신(참조). 사진 파일은 템플릿과 여행이 함께 쓰고, 템플릿 사진을 바꿀 때 여행이 아직 쓰는 파일은 지우지 않는다.
- **참가(Participation) 중심 인가** — 채팅·위치·공지·SOS·구독의 접근 권한을 "그 여행의 참가 여부" 하나로 통일하고, 한 곳에서 방 번호와 사용자로 참가를 한 번에 조회해 확인한다. 가이드도 여행을 열 때 참가자(role=GUIDE)로 등록되어 같은 경로를 탄다.
- **실시간과 영속의 이원화** — STOMP 브로드캐스트는 휘발, DB가 진실. 채팅은 전체 이력, 위치는 최신 스냅샷만 저장해 용도에 맞는 최소 데이터를 유지.
- **STOMP 프레임 3단계 인가** — HTTP 핸드셰이크는 열어 두되 CONNECT(JWT)·SUBSCRIBE(주소 형식 + 참가 확인)·SEND(주소 형식)를 인터셉터에서 막는다. 방 번호를 알아도 참가자가 아니면 구독할 수 없다. 메시지 처리 중 오류는 보낸 사람에게만 오류 큐로 알린다.
- **동시성은 잠금 한 가지 규칙으로** — 여행 행을 바꾸는 작업(참가 신청·취소, 정원 수정, 모집 마감, 삭제)은 그 행을 잠그고 시작한다. 참가 신청은 사용자 → 여행 순서로 잠가 데드락을 막고, unique 제약을 마지막 방어선으로 둔다.
- **시간은 한국 시간 하나로** — 모집 기간·스케줄러·저장 시각 등 '오늘'을 판단하는 곳은 모두 한국 시간 `Clock` 하나를 쓴다. 서버 시간대가 달라도 날짜가 밀리지 않는다.
- **외부 호출은 트랜잭션 밖으로** — S3 업로드, FCM 발송, 소셜 API 호출 동안 DB 커넥션을 잡지 않는다. S3 삭제는 DB가 커밋된 뒤에만 한다(롤백되면 파일을 지우지 않는다).
- **Docker 미도입 결정** — 초기에 Dockerfile을 작성했다가 제거했다(커밋 이력). 단일 EC2에 단일 jar를 올리는 구조에서 컨테이너 계층은 얻는 것(환경 일관성·오케스트레이션)보다 운영 복잡도가 컸다. 빌드 산출물(jar)을 SCP로 올려 재기동하는 GitHub Actions 파이프라인으로 충분했다.

### 4.3 빌드·배포 파이프라인

```
PR (main 대상) → GitHub Actions: gradle test (Testcontainers MySQL)

git push (main)
  → GitHub Actions: 설정 주입(Secrets → application-main.yml, Firebase 키) → gradle build
  → SCP로 EC2 전송 → 기존 프로세스 종료(fuser -k :8080) → nohup java -jar 재기동
```

민감 정보(DB 접속·JWT 시크릿·AWS 키·Firebase 서비스 계정)는 저장소에 두지 않고 GitHub Secrets에서 빌드 시점에 주입한다. 재기동 사이 수 초의 다운타임이 존재하는 단순 구조로, 무중단 배포는 도입하지 않았다.

### 4.4 네트워크·DB 접근 통제

- **RDS는 퍼블릭 접근을 차단**했다. 외부 인터넷에서 DB로 직접 붙을 수 없고, 애플리케이션 서버(EC2)는 VPC 내부 네트워크로만 RDS에 연결한다.
- DB 점검·관리가 필요할 때는 별도의 **Bastion Host(EC2)** 를 SSH 관문으로 두고, 개발자 로컬에서 Bastion을 경유해 RDS에 접근한다. DB를 인터넷에 노출하지 않으면서 관리 통로만 확보하는 구성이다.

## 5. 기획 대비 구현 범위

1학기 수행계획서의 구상과 최종 구현 사이에는 범위 조정이 있었다.

| 기획서 구상 | 최종 구현 |
| --- | --- |
| 결제·페이먼트 중개 (예약 시스템) | 미구현 — 가격 개념 자체를 제외 |
| AI 기반 가이드 추천 | 태그·지역·날짜·키워드 조합 검색으로 대체 |
| 1:1 개인 채팅 + 그룹 채팅 | 여행 그룹 채팅만 |
| 랜덤 코드/링크 그룹 참여 | 검색 → 참가 신청 플로우로 대체 |
| 호출(개인/전체) + 비상 호출 | SOS 긴급 호출(FCM)로 통합 |
| Docker/Kubernetes | 미사용 (단일 EC2 + jar) |
| Google/Kakao Maps | Naver Map SDK (클라이언트) |

반대로 기획서에 없던 것 중 구현 과정에서 추가된 구조도 있다: 템플릿-여행 분리 모델(여행 사본), 지역 부모/자식 계층 검색, 역할 전환의 JWT 재발급 체계, 여행 상태 자동 전환 스케줄러.

### 이후 과제 (현 코드 기준)

- STOMP 브로커가 내장 SimpleBroker이므로 수평 확장 시 외부 브로커(Redis pub/sub 등) 도입 필요
- FCM 푸시를 채팅·공지 알림으로 확장 (현재는 SOS만)
- 채팅 읽음 처리 (`participation.last_chat_read_at` 컬럼만 있고 갱신 로직은 연결되지 않음)

## 7. 기대 효과

- **여행자** — 취향에 맞는 소규모 여행을 찾는 비용이 줄고, 여행 중에는 위치 공유·SOS로 낯선 동행에 대한 불안이 완화된다. 리뷰·평점으로 가이드 선택의 근거가 축적된다.
- **가이드** — 자격증·여행사 없이도 자신의 코스를 상품화할 수 있고, 템플릿 재사용으로 여행을 열 때마다 드는 준비가 줄어든다. 운영 도구(공지·채팅·일정 변경)가 앱에 내장되어 별도 메신저 관리가 필요 없다.
